# ScrollShift website handover

## Canonical build model

This is a Nift website. Source lives in `content/` and `templates/`; generated output lives in `public/`.

Build with:

```bash
nift build-all
```

The committed `public/` tree must be generated by Nift from the current source. Do not hand-author generated HTML as a substitute for a Nift build.

## Nift relationship rules

Dogfood Nift's checked build relationships throughout the site:

- Use `@pathto('tracked/name')` for internal links to tracked pages.
- Use `@pathto('assets/...')` for tracked generated assets rather than hardcoded output URLs.
- Use `@input(...)` for shared source fragments so Nift records the dependency.
- Prefer checked relationships over unchecked strings whenever Nift can express the relationship.
- Do not replace these with root-relative `/docs/...` or `/assets/...` strings just because the generated path is known.

The shared docs navigation lives in `templates/docs-nav.html`. It uses built-in `name` metadata with constrained `@if` blocks to preserve active-page styling while keeping the navigation itself centralized.

## Structure

- `content/index.html` — short landing page.
- `content/docs/*.html` — documentation content.
- `content/assets/*` — tracked CSS, JavaScript and favicon sources.
- `templates/template.html` — shared document shell.
- `templates/head.html` — shared head metadata/assets.
- `templates/docs-nav.html` — shared documentation navigation.
- `.nift/tracked.json` — tracked page and asset names used by `@pathto`.
- `public/` — Nift-generated deployment output.

## Theme

The site supports system, light and dark modes. The explicit user choice is stored in `localStorage` under `scrollshift-theme`.

## Validation before committing

At minimum:

1. Run `nift build-all` from a clean `public/` directory.
2. Run `nift build-updated` and confirm the tree is already up to date.
3. Confirm no `@pathto`, `@input` or `@content` directives leaked into generated output.
4. Check generated internal links resolve to files in `public/`.
5. Keep claims evidence-scoped: distinguish proven hardware/desktop behavior from broader compatibility that remains untested.
6. Reconcile docs/roadmap and public status language whenever a new hardware, desktop or application compatibility result becomes proven.
